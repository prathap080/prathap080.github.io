The Single Most Important Thing
The exam tests judgment about tradeoffs, not memorization. Every multiple-choice question presents 4 plausible options. The correct answer is almost always: programmatic over prompt, structured over heuristic, root cause over symptom, proportionate first response, and preserve structure through the pipeline.

Five mental models

D1 · 27%
Agentic loop
A thermostat. Send → look at stop_reason → if tool_use execute and feed back; if end_turn stop. Never read text to decide whether to loop.
D2 · 18%
Tool design
A job description. If your description says "handles content," every tool applies. Be specific: purpose + inputs + outputs + when-to-use + edge cases + boundaries.
D3 · 20%
Claude Code
A team handbook. CLAUDE.md is the company manual at three levels (user, project, dir). Glob-pattern rules for files spread across folders. Plan mode = look before you leap.
D4 · 20%
Prompt engineering
The recipe vs. the dish. Few-shot beats prose. tool_use + JSON schema guarantees syntax (NOT semantics). Batch is the overnight delivery option.
D5 · 15%
Context management
The lossy compression problem. Summarization loses numbers/dates/IDs. Extract structured facts into a layer that survives summarization, hand-offs, and time.

Top 10 things you must know cold

  1. Loop control: while stop_reason == "tool_use"; stop on "end_turn". Never parse text.
  2. Subagent spawning: requires Agent (exam: Task) in allowedTools. Fresh context — pack everything in the prompt.
  3. Coordinator pattern: hub-and-spoke. Inter-subagent comms route through coordinator. Parallel = multiple Task calls in one response.
  4. Tool selection problems → improve descriptions first. Few-shot is second. Classifiers are over-engineering.
  5. Critical sequences (verify-before-refund) → hooks, not prompts.
  6. Structured errors: errorCategory, isRetryable, humanReadable.
  7. CLAUDE.md hierarchy: ~/.claude/ personal · project root shared · subdir scoped · .claude/rules/ for globs.
  8. Plan mode for architectural / multi-file / multi-approach. Direct for clear scoped fixes.
  9. Structured output: tool_use + JSON schema. tool_choice: any forces a tool; {type:"tool", name:"X"} forces a specific one.
  10. Batch API: 50% off, ≤ 24 h, no multi-turn tool calling. Never for blocking workflows.

The 4-step exam filter

  1. Eliminate "do nothing" / "switch model" / "wait and see" options.
  2. Eliminate "rely on probabilistic LLM behavior" when correctness is required.
  3. Eliminate over-engineered options when a proportionate response exists.
  4. Pick the option that addresses the root cause shown in the logs.

Domain 1 · Agentic Architecture & Orchestration

27% of examseven task statements · most-tested domain

The agentic loop

while True:
    response = client.messages.create(...messages, tools, system...)
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "end_turn":
        return response  # done

    if response.stop_reason == "tool_use":
        results = [execute_tool(b) for b in response.content if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})
        continue

Hub-and-spoke pattern

Right pattern
All inter-subagent communication routes through the coordinator. Subagents start with fresh context. Pack what they need into the prompt. Coordinator dynamically chooses subagents based on query.
Anti-pattern
Subagents calling each other directly. Loses observability. Complicates error handling. Breaks recovery semantics. Always route through the hub.
Parallel spawning
Coordinator emits multiple Agent tool calls in a single response. They run in parallel. Sequential = separate turns each. Massive perf difference on research workflows.
Coverage gap diagnosis
Synthesis misses subtopics + each subagent's outputs look fine? Coordinator's decomposition is too narrow. Don't blame downstream agents working correctly within scope.

Hook vs. prompt — when to use each

Use a hook when
Legal · financial · safety · regulatory · required ordering with consequences · compliance enforcement · data normalization across heterogeneous tools.
Use a prompt when
Style · soft preferences · tone · output format consistency (with few-shot) · "be polite" · non-critical ordering.

MCP tools vs. resources

Tools
Take an action / fetch dynamic data. Examples: create_issue, lookup_order. Cause a tool call.
Resources
Expose static or semi-static content catalogs. Examples: issue lists, doc hierarchies, DB schemas. Reduce exploratory tool calls — agent sees what's available upfront.

Plan mode vs. direct execution

Plan mode
Architectural changes · multi-file (10+) · multiple valid approaches · monolith → microservices · library migration · designing new caching layer.
Direct execution
Single-file bug fix with clear stack trace · adding a date validation · renaming a variable across known locations · implementing function with fixed signature.

CI/CD integration

# RIGHT — non-interactive, prints, exits
claude -p "Analyze this PR" \
  --output-format json \
  --json-schema review-schema.json
Non-existent flags (exam traps)
CLAUDE_HEADLESS=true · --batch · --non-interactive — these don't exist. Only -p / --print works.

Domain 4 · Prompt Engineering & Structured Output

20% of examyour strongest domain · six task statements

Vague vs. explicit criteria

Vague (doesn't work)
"Be conservative." · "Only report high-confidence findings." · "Have model self-report confidence and filter."
Explicit (works)
Allow-list of categories: bugs, security vulns, memory leaks. Deny-list: style preferences, naming inconsistencies. Include code examples per severity.

Few-shot prompting

  • 2-4 targeted examples beat 10 generic ones.
  • Cover ambiguous cases, not just easy ones.
  • Show the reasoning for choosing one action over plausible alternatives.
  • Demonstrate the desired output format precisely.

tool_use + JSON schema

tools = [{
    "name": "extract_invoice",
    "description": "Extract structured invoice data",
    "input_schema": INVOICE_SCHEMA,
}]

response = client.messages.create(
    model="claude-sonnet-4-5",
    tools=tools,
    tool_choice={"type": "tool", "name": "extract_invoice"},  # forced
    messages=messages,
)
Critical distinction
tool_use + JSON schema eliminates syntactic errors (no JSON parse failures, no markdown fences). It does NOT eliminate semantic errors (line items not summing to total, wrong field assignments). For semantic correctness, add paired stated/calculated fields with self-validation.

Schema design rules

Mark fields nullable/optional if source may not contain them→ model returns null instead of fabricating
Add "other" + detail field for extensible categorization→ avoid forcing wrong bucket
Add "unclear" enum for ambiguous cases→ explicit signal for human review
Add stated_total / calculated_total / match flag trio→ self-detect semantic errors

Retry with feedback

for attempt in range(max_retries):
    result = call_extraction_tool(messages)
    validation = validate(result, schema)

    if validation.ok: return result

    # Feed the SPECIFIC error back
    messages.append({"role": "user", "content":
        f"Validation failed: {validation.errors}. Please correct."
    })
Error typeRetry helps?
Format mismatch (date in wrong format)Yes
Schema validation (totals don't sum)Often
Required info genuinely absent from sourceNo — retry can't conjure data

Multi-pass review architecture

When to use
PR with 4+ files showing contradictory findings or inconsistent depth = attention dilution. Don't reach for "larger context window" — that doesn't fix it. Split into per-file passes + a cross-file integration pass.

Self-review trap

The bias
A model that just generated code retains its reasoning context — biased toward seeing the code as correct. Self-review (same session) catches fewer subtle issues. Even extended thinking doesn't fully fix it.
The fix
Spawn a separate Claude instance with no prior reasoning context for review. Fresh eyes catch issues the original missed.

Domain 5 · Context Management & Reliability

15% of examsmallest by weight, threads through every scenario · six task statements
Unifying theme
Structure outlives summarization. Anything important must be in a structured form that survives compression, handoffs, and time.

Persistent case facts

system_prompt = f"""

Escalation triggers

Valid triggers
Customer explicitly requests human · policy gap (silent on request) · agent has tried and can't progress · refund > policy limit (system-blocked).
Anti-pattern triggers
Sentiment / frustration alone · LLM self-reported confidence · heuristic "looks complicated" · multiple lookup matches (ask for ID instead).

Structured handoff payload

handoff = {
    "customer_id": "CUS-12345",

    "investigation_completed": ["Verified identity", "Confirmed eligibility"],
    "recommended_action": "Approve one-time match per goodwill guidance",
    "blocking_constraint": "Requires policy exception authorization",
}

Error propagation contract

{
    "subagent": "web_searcher",
    "failure_type": "timeout",
    "attempted_query": "...",
    "partial_results": [...],          # what we DID get
    "alternatives_attempted": [...],   # local recovery tried
    "alternatives_suggested": [...],   # for coordinator's recovery
}

Confidence calibration

ApproachVerdict
Aggregate accuracy (97%) sufficient for reducing reviewHides per-segment failures
Random sampling for accuracy validationOversamples common types
Stratified sampling per document type / per fieldRight approach
Field-level confidence calibrated to validation setRight approach
Self-reported confidence as quality gatePoorly calibrated
Self-reported confidence as routing-to-human signalOK if calibrated

Source provenance

{
  "claim": "AI assistants reduce review time by 30%",
  "source_url": "https://...",
  "source_document": "Dev Productivity Study 2025",
  "source_excerpt": "On average... 30% faster (n=234, p<0.01)",
  "publication_date": "2025-06-15",
  "methodology_context": "Survey-based, self-reported",
  "confidence": 0.85
}
Conflicting sources
When two sources disagree → annotate the conflict with both attributions and methodology context. Never arbitrate. Example: "Reuters reports 30% (survey, n=234) while McKinsey reports 18% (telemetry, n=1200) — methodology may explain the gap."

quick referenceeliminate these on sight

When you see one of these in a multiple-choice option, eliminate it. You don't need to know the right answer to remove the wrong ones — and removing 2 of 4 leaves a 50/50 you can usually reason through.

Decision frameworks

when to use what10 frameworks · master summary at the bottom

1 · Programmatic vs. prompt

Is the requirement legal/financial/safety/regulatory? ├── YES → Programmatic (PreToolUse hook with prerequisite gate) └── NO → Will incorrect behavior have material consequences? ├── YES → Programmatic └── NO → Could you tolerate ~95-99% reliability? ├── YES → Prompt instruction └── NO → Programmatic

2 · Plan mode vs. direct execution

Multi-file / architecture / cross-cutting? ├── YES → Plan mode └── Multiple valid approaches with different tradeoffs? ├── YES → Plan mode └── Path forward clear (single bug, scoped change)? └── YES → Direct execution

3 · Real-time vs. batch API

Will a human or system block waiting? ├── YES → Real-time └── Multi-turn tool calling needed? ├── YES → Real-time (batch lacks multi-turn) └── Tolerate ≤24h latency? ├── YES → Batch (50% off) └── NO → Real-time

4 · Skill vs. CLAUDE.md vs. rules vs. command

Auto-loaded (no user invocation)? ├── YES → Path-specific or universal? │ ├── Universal (every file) → CLAUDE.md (project root) │ ├── Per directory → CLAUDE.md (in that dir) │ └── Files spread across dirs by pattern → .claude/rules/ with paths glob └── User invokes on demand? ├── Just instructions → .claude/commands/<name>.md └── Multi-step workflow w/ own ctx → .claude/skills/<name>/SKILL.md

5 · Skill context: fork or not?

Will skill produce verbose intermediate output? ├── YES → context: fork (isolate; only summary returns) └── NO → Default (output goes into main conversation)

6 · Escalate, resolve, or continue?

Customer explicitly asked for human? ├── YES → Escalate immediately └── Request within agent capability AND policy? ├── YES → Resolve (acknowledge frustration first if any) └── Policy silent or conflicting? ├── YES → Escalate (policy gap) └── Agent tried and stuck? ├── YES → Escalate └── NO → Continue investigating

7 · Tool_choice modes

Need to guarantee structured output (no text)? ├── YES → Specific tool required first? │ ├── YES → tool_choice: {type:"tool", name:"X"} │ └── NO → tool_choice: {type:"any"} └── NO → tool_choice: {type:"auto"} (default)

8 · Few-shot vs. categorical criteria

Format consistency (output shape, JSON, naming)? ├── YES → Few-shot examples (show, don't tell) └── Judgment under ambiguity? ├── YES → Few-shot WITH reasoning shown └── Allow/deny categories? └── YES → Explicit categorical criteria

9 · Resume vs. fresh vs. fork

Prior context still valid (files unchanged, fresh)? ├── YES → Exploring divergent path from baseline? │ ├── YES → fork_session │ └── NO → --resume └── Files modified since prior? ├── YES → --resume + tell agent what changed └── Tool results stale (data shifted)? ├── YES → Fresh + structured summary └── NO → --resume

10 · Single-pass vs. multi-pass review

1-3 small filesSingle-pass
1-3 large or 4-6 smallSingle-pass with focus
4-10 files mixedMulti-pass: per-file + integration
10+ filesMulti-pass, possibly parallel
